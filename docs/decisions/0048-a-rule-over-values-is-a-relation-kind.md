# 0048. A rule over values is a relation kind: the restriction of one comparison to the orderings it admits

Status: accepted

## Context

A line over the threshold is discounted; an age is within the limits; an amount paid equals the amount due. A rule that compares values has two outcomes, and the page must declare both without a branch, a validator of its own, or an expression. The proof must read the same rule construction applies, or it decides from a second description of the rule and the two drift.

## Rejected

A `@computed_field` producing one of two constrained scalars from an expression (0002). A validator on the page. A relation whose refusal propagates as any other `ValidationError`: the run would end at the first line the rule did not hold for, instead of building the other outcome. One `model_validator` per relation kind beside a `constraints` tuple of `Constraint(less, than, by, strict)` declarations the proof read: two descriptions of one rule, the validator for construction and the constraints for the proof, named by field-name strings, and a relation kind that declared no constraints had to be refused as undecidable. A core-schema rewrite in `__get_pydantic_core_schema__` that reordered computed fields and wrapped them in a before-validator so that an ordering supplied in the input would be recomputed: sixty lines of schema surgery for what `Field(default_factory=...)` with validated data and `validate_default=True` do natively on 2.13.5.

## Decision

A relation is the restriction of one shared comparison to the orderings it admits. `Comparison(left, right)` is a `NamedTuple` naming two operand fields; called with the validated operands, it returns their ordering, -1, 0 or 1. `Compare[A, B, O](Relation)` holds `value: A` and `bound: B` and declares `ordering: Annotated[O, Field(default_factory=Comparison("value", "bound"), exclude=True, repr=False)]`: Pydantic computes the ordering at construction from the validated operands and admits it through the `Literal` type `O` or refuses it with `literal_error` at `("ordering",)`. The six relation kinds over two values are `Compare` with the admitted orderings fixed: `Under` admits -1, `AtMost` -1 and 0, `Equal` 0, `AtLeast` 0 and 1, `Beyond` 1, `Differs` -1 and 1; each is one line. `Between[A, L, U]` holds `value`, `lower` and `upper` and two ordering fields, `below` comparing `lower` against `value` and `above` comparing `value` against `upper`, each admitting -1 and 0. `Relation` has one `before` validator that drops any ordering key supplied in the input, so the only ordering is the computed one. A page declares the rule as a subclass with the compared classes as the parameters, `class Small(AtMost[LineTotal, Threshold])`, and each outcome as the fact that holds the relation that makes it true. The engine reads a refusal of a relation as the fact not holding in that scope, so the fact holding the relation that holds constructs and the other is never built; where the outcome is held, the union is the choice (0003). The proof reads the same fields: `comparisons(cls)` is each ordering field's `Comparison` and the orderings in its `Literal`, from `model_fields`, and from them it decides which relations are complements, which can never hold or never refuse, and which unions are exclusive (0051).

## Evidence

On Pydantic 2.13.5 with `Threshold` a constant of 100: `Small(AtMost[LineTotal, Threshold])` at a total of 100.00 constructed with `ordering` 0; at 125.00 it raised one error, `literal_error` at `("ordering",)`, "Input should be -1 or 0", input 1. `Large(Beyond[LineTotal, Threshold])` at 100.00 raised `literal_error`, "Input should be 1", input 0; at 125.00 it constructed with `ordering` 1. `Allowed(Between[Quantity, Quantity, Quantity])` with value 1, lower 1, upper 10 constructed with `below` 0, and with value 10 with `above` 0; with value 11 it raised `literal_error` at `("above",)`, input 1; with value 1 and lower 2 it raised `literal_error` at `("below",)`, input 1. `Same(Equal[Quantity, Quantity])` constructed for 3 and 3 and raised "Input should be 0" for 3 and 4; `Other(Differs[Quantity, Quantity])` constructed for 3 and 4 with `ordering` -1 and raised "Input should be -1 or 1" for 3 and 3; `Below(Under[Quantity, Quantity])` gave -1 for 3 and 4, `Above(AtLeast[Quantity, Quantity])` gave 0 for 4 and 4. `Small.model_validate({..., "ordering": 0})` at 125.00 raised `literal_error`: the supplied ordering was dropped and the computed one refused. `Small(...).model_dump()` was `{'value': {'left': Decimal('100.00'), 'right': 1}, 'bound': Decimal('100')}`, with no ordering. `Small.model_fields["ordering"].default_factory` was `Comparison(left='value', right='bound')`; the admitted orderings read with `get_args` were `(-1,)`, `(-1, 0)`, `(0,)`, `(0, 1)`, `(1,)`, `(-1, 1)` for the six kinds. In the engine's test program, `Low(AtMost[Amount, Limit])` with a limit of 10 valued an element at 2.50 as `Cheap` and an element at 25 as `Dear` holding `High(Beyond[Amount, Limit])` with `ordering` 1.

## Consequences

Unwritable: a validator on a page; a comparison in a computed field; a second description of a rule for the proof. A relation kind written outside the world subclasses `Relation` and declares ordering fields the same way, and the proof reads it without change; a relation kind that declares no ordering field never refuses, and the proof refuses it as `never`. Refuted by a relation over values that are not numbers; that is a comparison over another root type, declared the same way.
